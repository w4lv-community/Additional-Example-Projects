# Workers <-> Python gRPC Scope Example

This example demonstrates a Workers gRPC Server Worker communicating with a Python application over a bidirectional gRPC stream. The example is based on the gRPC Server Worker Template (available from the Worker User Library) with selected message payloads in `scope.proto` modified to send scope configuration, state, device information, and waveform data. The message names in `scope.proto` are unchanged from the template; only the payloads differ.

## Dependencies

**Install these before opening the project.** The example will not run without them.

Download [grpc-labview.zip](https://github.com/ni/grpc-labview/releases/download/v1.7.0.1/grpc-labview.zip) from the NI gRPC LabVIEW repository on GitHub and install the three VI packages it contains:

| VI package |
| --- |
| `ni_lib_labview_grpc_library-1.7.0.1.vip` |
| `ni_lib_labview_grpc_servicer-1.7.0.1.vip` |
| `ni_lib_grpc_server_and_client_template[2]-1.7.0.1.vip` |

LabVIEW 2019 or later is required.

## What is in the project

| Item | Purpose |
| --- | --- |
| `scope.proto` | The Public API contract. The generated code on both ends derives from this file. |
| `Generated_server.lvlib` | NI gRPC generator output. |
| `gRPC Server (scope.proto).lvlib` | gRPC Server Worker. Creates the gRPC server and handles the bidirectional stream. |
| `Head_ScopeSim.lvclass` | Head Worker. Launches the gRPC Server Worker and the Scope Simulator. |
| `Scope Simulator.lvclass` | The Worker that generates the simulated scope waveform. |
| `Launcher - Head_ScopeSim.vi` | Launches the Workers application. |
| `client-py/scope_panel.py` | The Python oscilloscope user interface. |
| `client-py/stubs/` | Python stubs generated from `scope.proto`. |

## Run the Example

1. Run **Launcher - Head_ScopeSim.vi** to launch the Workers application. Press **Create gRPC Server** and wait for the **Server Listening** LED to light.

2. Run `client-py/scope_panel.py` to launch the Python scope application. Connect to the server. The **Client Connected** LED in LabVIEW and **CONNECTED** status in Python indicate that the bidirectional stream is open.

3. Use the two applications together:

   * Press the **RUN** button on the Python application to start the LabVIEW Scope Simulator.
   * In the LabVIEW Scope Simulator, select the waveform type (**select**) and adjust its **amplitude** and **frequency**. These controls determine the simulated scope output. The Python application scope display should match the waveform generated by the LabVIEW Scope Simulator.
   * In the Python application, change the physical channel, sample rate, or samples per read and press **APPLY** to send the configuration message to LabVIEW. The example demonstrates that this data is transmitted over gRPC, but the Scope Simulator does not currently use these values in its simulation logic.
   * Use **RUN** / **STOP** in the Python application to control acquisition.
   * LabVIEW continuously sends the simulated waveform, scope state, device information, and acquisition count to the Python application over the same bidirectional stream.

4. When finished, disconnect the Python application by pressing **DISCONNECT**.

5. Press **Destroy gRPC Server** in the Workers application to close the stream and stop the server.

## How the scope.proto file maps to the application

Five of the eighteen available template messages are used. The rest remain as placeholders.

| Message Name | Payload | Sent when |
| --- | --- | --- |
| `Msg_ToServer_1` | `physical_channel`, `sample_rate_hz`, `samples_per_read` | **APPLY** pressed |
| `Msg_ToServer_2` | `run` | **RUN** or **STOP** pressed |
| `Msg_ToClient_1` | `device`, `product_type` | On connect |
| `Msg_ToClient_2` | `y`, `dt`, `t0`, `label`, `acquisitions` | Each acquisition |
| `Msg_ToClient_3` | `state` | On state change |

The name of each message tells you its direction. Client to server carries commands, server to client carries data and status.

## Adapting the example

Fill the free messages in `scope.proto` with the payloads your application needs, regenerate the LabVIEW library, and replace it in your project. Because the frozen names are unchanged, everything else stays put.

For a full walk through of this process, including the code generation, see [Using the gRPC Worker Templates](https://community.workersforlabview.io/private-articles/post/using-the-grpc-worker-templates-nZFACBeQcmMJnXm).

## Notes

**Real-time targets are untested.** The NI gRPC library supports NI Linux RT with system image 2022 Q4 or later, but this example has not been verified on an RT target.
